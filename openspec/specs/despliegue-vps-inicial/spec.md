# despliegue-vps-inicial Specification

## Purpose

Definir el despliegue inicial de la imagen `libreria` en el VPS sin datos semilla, usando `docker run` + `--env-file` (sin Docker Compose), con publicación de puerto, reinicio automático, conexión a la base fuera del contenedor (contenedor Postgres de EasyPanel unido por red Docker) y verificación observable de salud, no-root y fallo esperado ante ausencia de `DATABASE_URL`.

## Requirements

### Requirement: Despliegue inicial en VPS con contrato de ejecución y recuperación a healthy (D-02, D-06)
El despliegue inicial SHALL ejecutarse en el VPS con la imagen `libreria` construida en el servidor (`git pull` + `docker build -t libreria .`) mediante `docker run` en modo desacoplado, con nombre `libreria`, unido a la red de la base con `--network <RED_DOCKER>`, puerto publicado `<PUERTO_PUBLICO>:8000`, política `--restart unless-stopped` y configuración provista por `--env-file <ARCHIVO_ENV_SERVIDOR>` ubicado en el servidor fuera del repo y de la imagen. La base corre como contenedor de EasyPanel (Postgres) y `DATABASE_URL` SHALL usar como host el nombre del servicio de la base `<HOST_BASE>` (nunca `localhost`) con driver `postgresql+asyncpg`; no se SHALL publicar el puerto 5432 de la base. `--add-host=host.docker.internal:host-gateway` queda como alternativa solo para una base instalada en el host, usando `host.docker.internal` como host en `DATABASE_URL`. Con base alcanzable y configuración válida, el contenedor SHALL quedar `healthy`, el proceso NO SHALL correr como root, y SHALL volver a quedar `healthy` tras `docker rm -f libreria` seguido del mismo `docker run` de despliegue.

#### Scenario: (Esperado) Despliegue limpio, no-root y recuperación a healthy tras recreación
- **WHEN** en el VPS se obtiene el código (`git pull`) y se construye la imagen `libreria` (`docker build -t libreria .`), se prepara `<ARCHIVO_ENV_SERVIDOR>` en el servidor (fuera del repo/imagen) con `DATABASE_URL` apuntando al host `<HOST_BASE>` y `SQL_ECHO=false`, se ejecuta `docker rm -f libreria` (ignorando si no existe) y luego `docker run -d --name libreria --network <RED_DOCKER> -p <PUERTO_PUBLICO>:8000 --restart unless-stopped --env-file <ARCHIVO_ENV_SERVIDOR> libreria`, se espera a que el healthcheck estabilice, y posteriormente se repite `docker rm -f libreria` seguido del mismo `docker run`
- **THEN** la salida real de `docker ps --filter name=libreria` muestra el contenedor en ejecución y `healthy` después del despliegue inicial y nuevamente después de la recreación; `docker inspect libreria --format "{{.State.Health.Status}}"` responde `healthy` en ambos casos; `docker inspect libreria --format "{{.HostConfig.RestartPolicy.Name}}"` muestra `unless-stopped`; `docker exec libreria id` muestra un uid distinto de 0 (D-06); `docker logs libreria` muestra el arranque completo con las tablas creadas (D-02); y una solicitud real `curl -i http://<HOST_PUBLICO>:<PUERTO_PUBLICO>/health/ready` (o equivalente desde el punto de verificación acordado) devuelve respuesta HTTP 200 con cuerpo de estado (D-02), siempre que la base esté alcanzable. Evidencia: salidas reales de `git pull`/`docker build` (si aplica), `docker run`, `docker ps`, `docker inspect`, `docker exec libreria id`, `docker logs libreria` y `curl`.

### Requirement: Sin DATABASE_URL el contenedor no queda sirviendo (D-05)
Si `DATABASE_URL` no está provista por el archivo de variables/configuración efectiva, el proceso SHALL fallar al arrancar y el contenedor NO SHALL quedar sirviendo (ni `running` ni `healthy`). La interpretación del código de `/health/ready` ante fallo de base permanece sujeta a `knowledge-base/10_preguntas_abiertas.md` §(2) (pendiente de cátedra); este requisito verifica el comportamiento observable de arranque/configuración sin `DATABASE_URL`.

#### Scenario: (Error de negocio/configuración) Arranque sin DATABASE_URL termina sin quedar en servicio
- **WHEN** en el VPS se ejecuta `docker rm -f libreria` (ignorando si no existe) y se corre `docker run --name libreria --network <RED_DOCKER> libreria` sin `--env-file` y sin `DATABASE_URL` en el entorno efectivo
- **THEN** el comando termina con error (código distinto de 0) y la salida real de `docker ps -a --filter name=libreria` muestra el contenedor en estado `Exited` (o equivalente no `running`/no `healthy`), nunca `running`/`healthy` (D-05). Evidencia: salidas reales de `docker run` (o su código de salida), `docker ps -a --filter name=libreria` y, si aplica, `docker logs libreria` mostrando el fallo de arranque/configuración.

### Requirement: La base no se alcanza por localhost desde el contenedor (borde de red/host)
Una `DATABASE_URL` que use `localhost` como host SHALL ser inalcanzable desde el contenedor (dentro del contenedor `localhost` es el propio contenedor). En el despliegue con base en contenedor de EasyPanel, la corrección SHALL usar `<HOST_BASE>` como host en `DATABASE_URL` y unir el contenedor a la red de la base con `--network <RED_DOCKER>` (nunca `localhost`, sin publicar el puerto 5432). `--add-host=host.docker.internal:host-gateway` y `host.docker.internal` quedan como alternativa solo para una base instalada en el host.

#### Scenario: (Borde) Configuración con localhost falla y la corrección usa HOST_BASE + RED_DOCKER
- **WHEN** en el VPS se usa un `<ARCHIVO_ENV_SERVIDOR_LOCALHOST>` (archivo temporal equivalente en el servidor, fuera del repo) cuya `DATABASE_URL` apunta a `localhost`, y se ejecuta `docker rm -f libreria` seguido de `docker run --name libreria --network <RED_DOCKER> --env-file <ARCHIVO_ENV_SERVIDOR_LOCALHOST> libreria` (sin `--rm`)
- **THEN** el contenedor termina en estado `Exited` y la salida real de `docker logs libreria` muestra un error de conexión (p. ej. `ConnectionRefusedError` o `Connect call failed` de asyncpg), evidenciando que `localhost` no alcanza la base desde el contenedor. La corrección documentada y aplicada para el despliegue válido es usar `DATABASE_URL` con host `<HOST_BASE>` y `--network <RED_DOCKER>` (nunca `localhost`, sin publicar el puerto 5432 de la base). Evidencia: salidas reales de `docker ps -a --filter name=libreria` y `docker logs libreria` para el caso fallido, y salida real de `docker inspect libreria --format "{{json .HostConfig.NetworkMode}}"` (o inspección equivalente) mostrando la red `<RED_DOCKER>` en el despliegue corregido.
